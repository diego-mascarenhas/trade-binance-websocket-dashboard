1. Arquitectura

El sistema usa Binance Futures USDT-M de punta a punta: señales por WebSocket (fstream: velas, depth, miniTicker) y ejecución opcional por REST (fapi).

  • Un proceso por par (app.py SYMBOL --port 805x): stream WS, cálculo de señal, dashboard individual.
  • Hub central (hub_server.py, puerto HUB_PORT, default 8050): tarjetas de todos los pares vía proxy interno.
  • Flota (./run-all.sh): arranca hub + 16 dashboards + listener Telegram + fapi_watch.
  • Analytics (/analytics/): KPIs, bloqueos, export CSV para ML (requiere MySQL opcional).

Los puertos 8051–8072 solo deben ser accesibles en 127.0.0.1. El hub los consulta por proxy; no abras esos puertos al firewall público.

2. Pipeline de señales

Hay tres niveles distintos. Confundirlos explica la mayoría de dudas:

Nivel Condición Qué hace
NEUTRAL Sin LONG/SHORT o confianza < mínimo Solo observación. No hay plan activo.
WATCH LONG o SHORT pero confianza < MIN_CONFIDENCE (default 50%) Se muestra dirección tentativa. No es entrada válida.
TRADE LONG/SHORT y confianza ≥ MIN_CONFIDENCE Setup visible en hub. Aún puede bloquearse antes de ejecutar.
Valid entry TRADE + alineación HTF + filtros + debounce + plan activo + cooldown Registra entrada, alerta Telegram y (si está activo) envía orden Futures.

Flujo resumido:

Depth WS → candidato (LONG/SHORT/NEUTRAL)
         → debounce (N lecturas iguales)
         → filtros RSI/ADX/MACD
         → alineación con tendencia HTF
         → plan de trade activo
         → valid entry → ejecución (si EXECUTION_ENABLED)

3. Señal por order book

La señal principal usa el libro de órdenes (muros de volumen como soporte/resistencia dinámicos):

  1. Se identifican el muro de compra más grande (soporte) y el de venta (resistencia).
  2. Se calcula la posición del precio en el rango soporte–resistencia (0–100%).
  3. Con histeresis para evitar flip-flop:
    • LONG entra si posición ≤ SIGNAL_ZONE_LONG_ENTER (default 20%). Sale a NEUTRAL si sube por encima de SIGNAL_ZONE_LONG_EXIT (35%).
    • SHORT entra si posición ≥ SIGNAL_ZONE_SHORT_ENTER (80%). Sale a NEUTRAL si baja de SIGNAL_ZONE_SHORT_EXIT (65%).

Confianza por zona OB

  • Cerca de soporte (LONG): 65% + 15% extra si 24h < −3% (reversal).
  • Cerca de resistencia (SHORT): 65% + 15% extra si 24h > +3%.

Fallback por cambio 24h

Si no hay señal de zona, usa @miniTicker:

  • 24h > +5% → SHORT 50% (extremo alcista)
  • 24h < −5% → LONG 50% (extremo bajista)
  • 24h > +2% → LONG 40% (no alcanza TRADE por defecto)
  • 24h < −2% → SHORT 40%

Sin bids/asks (WS en connecting) no se calcula señal: el proceso retorna antes de analizar el libro.

4. Análisis HTF / SMC / patrones

Tendencia HTF (HTF_INTERVAL, default 15m)

EMA rápida (EMA_FAST 9), lenta (EMA_SLOW 21) y de tendencia (HTF_EMA_TREND 50):

  • BULLISH: cierre > EMA50 y EMA9 > EMA21
  • BEARISH: cierre < EMA50 y EMA9 < EMA21
  • NEUTRAL: resto de casos

SMC (Smart Money Concepts)

En velas HTF y LTF detecta estructura: BOS, CHoCH, variantes internas (iBOS, iCHoCH), liquidez igual (EQH/EQL), sweeps y zona Premium/Discount.

  • Swings fractales: SMC_SWING_LEFT/RIGHT (HTF), SMC_INT_SWING_LEFT/RIGHT (LTF).
  • Lookback rupturas: SMC_BREAK_LOOKBACK_HTF (3), SMC_BREAK_LOOKBACK_LTF (12).
  • Premium/Discount: ≤ SMC_PD_DISCOUNT_MAX (38%) = Discount; ≥ SMC_PD_PREMIUM_MIN (62%) = Premium.
  • Tolerancia EQ: SMC_EQ_TOLERANCE_PCT (0.08%).

Patrones de vela (gráfico individual)

  • Hammer → confirma LONG (cuerpo pequeño, mecha inferior larga, contexto bajista o cerca de soporte).
  • Shooting Star → confirma SHORT (contexto alcista o cerca de resistencia).
  • Rango mínimo de vela: MIN_PATTERN_RANGE_PCT (0.02%).

Los patrones refuerzan visualización; la señal operativa principal sigue siendo order book + 24h.

5. Filtros y bloqueos

Con INDICATOR_FILTERS_ENABLED=true (default), antes de un valid entry:

Filtro Variable Default Bloquea si…
RSI RSI_FILTER_ENABLED true LONG con RSI > RSI_LONG_MAX (70); SHORT con RSI < RSI_SHORT_MIN (30)
ADX ADX_FILTER_ENABLED true ADX < ADX_MIN_TREND (25). Usa HTF si ADX_USE_HTF=true.
MACD MACD_FILTER_ENABLED false LONG con histograma < 0; SHORT con histograma > 0
HTF align REQUIRE_TREND_ALIGN true LONG sin HTF BULLISH; SHORT sin HTF BEARISH; HTF NEUTRAL bloquea todo
Debounce SIGNAL_DEBOUNCE_COUNT 5 Candidato debe repetirse 5 veces seguidas en actualizaciones de depth
Cooldown SIGNAL_COOLDOWN_SEC 180 s Mínimo entre valid entries del mismo par
Plan — — Sin plan activo (SL/TP no calculables)
Flota pausada logs/fleet.state — trading_paused=true → no envía órdenes (señal TRADE puede seguir visible)
Balance L/S FLEET_SIDE_BALANCE_MAX_PCT 20% Un lado (long o short) supera al otro más del 20% en USDT
Par deshabilitado symbol_trading_enabled true Override MySQL por par

En el hub, la sección Blocked resume:

  • low signal N — pares en NEUTRAL o 0% confianza
  • HTF mismatch N — TRADE visible pero señal ≠ tendencia HTF
  • aligned N — TRADE alineado con HTF
  • fleet paused — ejecución detenida globalmente
  • auto exec off — EXECUTE_ON_VALID_ENTRY=false

6. Plan de trade (SL, TP, DCA, break-even)

Cuando hay TRADE con plan activo, se calculan niveles estructurales:

Entrada y DCA

  • Primera pierna: TRADE_PLAN_INITIAL_SIZE_PCT del wallet (default 50%).
  • Pasos DCA: TRADE_PLAN_DCA_STEPS (2) espaciados TRADE_PLAN_DCA_STEP_PCT (2.5%) desde entrada.
  • Modo compensación (TRADE_PLAN_DCA_COMPENSATION=true): cada banda adversa añade entry_usdt × band% × TRADE_PLAN_DCA_COMP_USDT_PER_PCT.
  • TRADE_PLAN_DCA_SIGNAL_DRIVEN=true: una pierna DCA por cada valid entry (no todos los límites a la vez).
  • TRADE_PLAN_DCA_ADVERSE_ONLY=true: DCA solo si posición en pérdida (DCA_FAVORABLE_PNL_MAX_USDT ≤ 0).

Stop loss y take profit

  • SL bajo estructura (soporte/resistencia) con buffer TRADE_PLAN_SL_BUFFER_PCT (0.25%).
  • Distancia mínima entry–SL: TRADE_PLAN_SL_MIN_DISTANCE_PCT (1%).
  • TP1 = riesgo × TRADE_PLAN_TP1_RR (1.0); TP2 × TRADE_PLAN_TP2_RR (2.0).
  • Cierre parcial ~TRADE_PLAN_PARTIAL_CLOSE_PCT (70%) al detectar TP1.

Break-even y trailing

  • TRADE_PLAN_AUTO_BE=true: mueve SL a entrada tras parcial o por señales (BE_TRIGGER_PARTIAL, BE_TRIGGER_SIGNAL).
  • Triggers de señal: HTF neutral/contra, SMC ranging, RSI extremo (BE_ON_*).
  • TP tipo trailing: TP_ORDER_TYPE=trailing, callback TP_TRAILING_CALLBACK_RATE (0.5%).
  • Reprice SL/TP si drift > SL_REPRICE_TOLERANCE_PCT / TP_REPRICE_TOLERANCE_PCT.

7. Ejecución en Binance Futures

  • EXECUTION_ENABLED=false por defecto. EXECUTION_MODE=dry solo registra; live envía órdenes.
  • EXECUTE_ON_VALID_ENTRY=true: orden automática al confirmar valid entry.
  • Tamaño: POSITION_SIZE_USDT (25) o POSITION_WALLET_PCT si > 0.
  • Apalancamiento: LEVERAGE (4) o LEVERAGE_MODE=max (máximo del símbolo).
  • Primera pierna: ENTRY_FIRST_LEG_MARKET=true (MARKET + SL/TP desde fill real).
  • DCA adicionales: órdenes LIMIT.
  • Órdenes LIMIT de entrada sin fill: canceladas tras ENTRY_LIMIT_TTL_SEC (600 s).
  • Cooldown entre órdenes: EXECUTION_ORDER_COOLDOWN (180 s).
  • Mantenimiento SL/TP: cada EXECUTION_MAINTENANCE_SEC (60 s).
  • No abre si ya hay posición, límite conflictivo o duplicado (EXECUTION_BLOCK_IF_OPEN).

9. ¿Cuánto tarda en haber señales?

Sí, pueden pasar horas sin ninguna señal TRADE ejecutable. Es comportamiento esperado cuando:

  • El precio está en la zona media del rango OB (35–65%) → NEUTRAL prolongado.
  • HTF en NEUTRAL → ningún valid entry con REQUIRE_TREND_ALIGN=true.
  • ADX bajo (< 25) → mercado sin tendencia clara.
  • Movimientos 24h moderados (±2%) → solo 40% confianza, quedan en WATCH.
  • Varios pares en connecting → sin libro de órdenes, sin señal.

Tiempos de referencia (con datos en vivo):

  • Debounce: ~5 × DEPTH_METRICS_INTERVAL_SEC ≈ 1.25 s mínimo (si depth estable).
  • Cooldown entre entradas del mismo par: SIGNAL_COOLDOWN_SEC (180 s).
  • Hub refresh: 5 s. UI individual: METRICS_INTERVAL_MS (8000 ms default).
  • WS ping: cada WS_PING_INTERVAL (20 s), timeout WS_PING_TIMEOUT (120 s).

Si todos los pares muestran precio «—» y connecting durante mucho tiempo, revisa que ./run-all.sh esté activo y que los procesos escuchen en los puertos de hub/pairs.json.

10. Anti-baneo y rate limits

Binance limita REST y puede bloquear IP (HTTP 418, 403 CloudFront, 429 / -1003). El sistema incluye varias capas:

fapi_watch (vigilancia REST)

  • Activo con ./run-all.sh (hilo en telegram_fleet.py).
  • Prueba GET /fapi/v1/ping cada FAPI_WATCH_INTERVAL_SEC (900 s = 15 min).
  • Si falla (403, 418, CloudFront, timeout): pausa trading (= /stop) y alerta Telegram.
  • Cooldown de alertas repetidas: FAPI_WATCH_COOLDOWN_SEC (3600 s).
  • Al recuperar HTTP 200: notifica pero no reanuda solo — envía /start manualmente.
  • Desactivar: FAPI_WATCH_ENABLED=false.

Cache REST compartida (flota)

  • FLEET_REST_CACHE_ENABLED=true: un solo positionRisk + openOrders para todos los pares.
  • TTL: FLEET_REST_CACHE_SEC (60 s). Archivo: logs/fleet_rest_cache.json.
  • Cache de posición por par: EXECUTION_POSITION_CACHE_SEC (60 s).
  • Cache cuenta/PnL: ACCOUNT_SNAPSHOT_CACHE_SEC (60 s).
  • Exposición L/S flota: FLEET_EXPOSURE_CACHE_SEC (60 s).

Backoff automático

  • Ante error -1003 / «banned until», parsea timestamp y deja de llamar REST hasta esa hora.
  • Durante backoff usa último cache disponible en lugar de golpear la API.

WebSocket vs REST

  • Señales usan WebSocket Futures (FSTREAM_WS_BASE, default wss://fstream.binance.com).
  • REST fapi para bootstrap al conectar (depth/klines) y para ejecución, posiciones, SL/TP — minimizado por caches.
  • DEPTH_METRICS_INTERVAL_SEC=0.25: recalcula señal como máximo 4×/s (libro sigue actualizándose cada tick).
  • METRICS_INTERVAL_MS=8000: UI hace menos lecturas REST.

Buenas prácticas

  • No abras puertos 8051+ al público; usa solo el hub (8050) detrás de nginx.
  • Un solo proceso debe hacer polling Telegram (getUpdates) — evita 409 Conflict.
  • Si ves 418 en el hub: espera o cambia IP del VPS; no fuerces REST.
  • Prueba manual: .venv/bin/python scripts/check_fapi_health.py --dry-run

11. Telegram y flota

Variables: TELEGRAM_BOT_TOKEN, TELEGRAM_CHAT_ID.

Comandos (solo el chat autorizado, un listener con ./run-all.sh):

  • /status — resumen flota: TRADE, posiciones abiertas, offline
  • /stop — pausa trading en todos los pares
  • /start — reanuda trading

Alertas automáticas: valid entry, apertura/cierre, errores de orden (cooldown ORDER_FAIL_NOTIFY_COOLDOWN 120 s), bloqueo fapi_watch.

Estado compartido en logs/fleet.state (trading_paused, fleet_running).
